## Phase 11a — Hostile-node review  (2026-09-03)

A pass over "what can a node that is lying to me do", with a three-node
cluster and a Byzantine HTTP server standing in for a hostile node.

Three real gaps in the light client, all of the same shape — trusting one
node's answer without checking it against what was asked (whitepaper §12
says the opposite):

- `NodeClient::item` did not check that the item it got back is the one it
  asked for. A single node could answer a `vote_id` query with a **decoy vote
  definition** (same question, options swapped, correctly authority-signed):
  the device would then build a ballot for the decoy's `vote_id`, and the
  voter's own "is my nullifier anchored?" check would pass against that same
  lying node. The voter would believe they had voted while their ballot sat in
  a vote nobody counts. Now the answer must hash to the requested content id
  (`ClientError::WrongItem`); `item_by_hash` likewise.
- `NodeClient::registry` ignored the snapshot: no signature check, no check
  that it is the requested `(issuer_key, root)`, no leaf count. Now all four
  are checked (`ClientError::BadRegistry`).
- `ParticipantClient::participant` did not check that the leaves the node
  served rebuild the root the vote names, so a node could make the device
  prove membership of a tree of its own (a silent disenfranchisement, since
  every honest node then rejects the ballot). Now `ForgedLeaves`.
- `select_parties` took each key party's `pk` from the node's summary. A node
  could substitute a key and make the ballot undecryptable, so the vote is
  cast but never counted. The `pk` now comes from the KeyParty item itself,
  fetched by content id.

`crates/node/tests/adversarial.rs` (new, 3 tests):
`forged_items_are_refused_by_every_node` — tampered payload with a valid
proof, a re-randomized proof (accepted as a retransmission, and it does not
knock the voter's ballot out: A3), an invented proof, a ballot replayed into
another vote, a vote signed by a non-authority, a vote over a root its named
Issuer never signed, a witness from an unregistered node, an anchor at a
height with no header, an anchor over an id that does not exist, and a
genuine double vote — none of which moves a count, on any of the three nodes
or in the verifier's independent recomputation.
`an_unrecognised_issuer_is_isolated_from_another_electorate` — an Issuer
nobody recognises gets its own electorate and nothing else; a cross-registry
ballot is refused; a root claimed under the wrong Issuer never resolves; a
person in both registries has unlinkable nullifiers in the two votes.
`a_lying_node_cannot_redirect_or_bury_a_ballot` — a Byzantine node that
serves a decoy vote, a foreign-signed registry and forged leaves, and that
claims to accept ballots and drops them: every lie is caught client-side, and
the voter recovers by reaching the one honest node, with an anchor inclusion
proof as evidence that their ballot was in the anchored root.

Each of the three client checks was re-verified by removing it and watching
the test fail.

One bug outside the protocol, found by running the binaries rather than the
tests: `cv-node --dev` never finished starting. arkworks opens a `tracing`
span per R1CS constraint under the target `gr1cs`, and the node's log filter
enabled `info` globally, so the development Groth16 setup went from ~0.1 s to
minutes of span bookkeeping. The node binary was therefore unusable in dev
mode exactly as the README documents it (`cv-sim` was unaffected because it
filters at `warn`, and `cv-client` installs no subscriber at all). Fixed by
pinning `gr1cs=warn` in the node's filter. Release builds load ceremony keys
instead of running the setup, and proof *verification* synthesizes no
constraints, so nothing else was affected.

## Phase 11b — "Anchored" is now checked, not believed  (2026-09-04)

The remaining single-node-trust hole, and the worst of them: both
confirmation paths (`ParticipantClient::confirm`, `MixClient::cast_with_retry`)
took the node's `anchored_height` at face value. A node that dropped a ballot
could simply answer "anchored at height H", and the voter would **stop
resending** — the one thing the whitepaper §12 client is supposed to do. That
turns a node that can only censor into a node that can disenfranchise
silently.

- `cv-core`: the anchor-proof rule is factored into
  `validate::check_anchor_proof(proof, root, block_root, dev_mode)`, so nodes,
  the verifier and now the client all reach the same implementation
  (`validate_anchor` calls it).
- `cv-client::evidence` (new): `anchor_evidence()` fetches the anchor and an
  inclusion proof, **recomputes** the Merkle root from the anchor's own
  leaves, requires the ballot's content id to be a leaf of it and the proof to
  verify against that recomputed root, and then — given block headers — checks
  the anchor's OTS/direct proof against Bitcoin. The result carries how far
  the check got (`Bitcoin` / `MerkleOnly` / `Dev`) and can be rechecked
  offline, so it is also the voter's evidence that their ballot was in.
  Dev anchors are refused unless dev mode is explicitly asked for.
- `cv-client`: `confirm`/`confirm_evidence` return only checked anchors;
  `MixClient::anchored_height` became `claimed_status` (a hint about which
  content ids to check, never a confirmation); `--headers <file>` on the CLI
  supplies the chain, and without it the CLI says plainly that the Bitcoin
  half is unchecked.
- Tests (`a_lying_node_cannot_redirect_or_bury_a_ballot`): a node that claims
  height 150 and backs it with an anchor of its own plus a well-formed
  inclusion proof for a leaf that is not the ballot is not believed; a real
  dev anchor is not believed either unless dev mode is asked for; the honest
  node's anchor checks out and the evidence re-verifies offline.

## Phase 11c — Fallback witnesses scoped to the electorate  (2026-09-04)

A hole opened by Phase 11 itself. The §9 fallback counts a ballot when `W = 7`
distinct *registered* nodes attest they held it before close. Under one Issuer
that is a Sybil bound — seven registrations are seven people. Under several
Issuers it is not: an attacker publishes their own registry, enrols seven of
themselves, registers seven nodes, and backdates ballots into any vote that
has no anchor. Nothing else about that attacker's Issuer has to be believed by
anyone; a node that stores any registry (the open default) accepts the
registrations as the valid items they are.

`tally::timely_ballots` now counts a witness only if its node's registration
names the vote's own `issuer_key` (SPEC §12, §6.8, A49). Other electorates'
registrations stay valid items and are still relays and mix hops. Verified by
removing the check and watching the new test
`fallback_witnesses_must_come_from_the_votes_own_electorate` count the
attacker's backdated ballot.

Nothing about *running* a node changed, and nothing about it ever needed the
Issuer: storing, validating, relaying and anchoring are open to anyone with no
registration and no permission. A registration is only needed to be picked as
a mix hop by other people's clients (one person one hop, or the anonymity set
is Sybil'd) and to sign fallback witnesses.

## Phase 11d — Per-electorate identity, hops on by default  (2026-09-04)

Prompted by the question "so I have to be approved by the state before I can
run a node?" — the answer is no, and the code had two things that made it look
otherwise, plus one that made hops hard to have at all.

- **Nothing is globally scoped any more.** The node-registration nullifier and
  the author pseudonym used `id = 0`, so they were identical in every registry
  a person belonged to. That linked one person's activity across electorates
  for no benefit, and — worse — meant a person enrolled with two Issuers could
  hold exactly **one** node registration in total: registering in the second
  electorate collided with their own first registration and the duplicate rule
  destroyed both. Both now use `id = fr_mod(issuer_key)`: one node per person
  per electorate, one pseudonym per person per electorate, no cross-electorate
  linkage. The circuit is untouched (`id` is a public input it never
  interprets). SPEC §3.1, §4.3, §6.2, §6.7, §7.1; A50.
- **Being a mix hop is on by default.** The node generates and persists its own
  X25519 mix key and Ed25519 identity key in its store, prints both at startup
  with the exact command to register them, and serves `/v1/mix`; `--no-mix`
  opts out. Witnessing stays opt-in (`--witness`) since it adds an item per
  ballot and only matters when a vote has no anchor.
- **`cv-client register-node`** — there was no way to publish a
  NodeRegistration outside the tests. Now there is, and the CLI casts through
  the mix by default (`--no-mix` for direct).
- **Hop diversity is tiered instead of all-or-nothing.** `diverse_from`
  required distinct operator *and* ASN *and* country, so a network whose nodes
  are mostly in one country — every national deployment — collapsed to
  one-hop paths. The client now takes the most diverse path it can build
  (full → same-country → distinct-nodes) and reports which it got, the same
  way it reports Tor. A live five-node network went from
  "partial: 1 mix hop(s)" to "partial: 3 mix hop(s), 2 path(s), same country".
- A51 records the baseline the design now assumes: enough hops for a
  three-hop path, and at least one honest node reachable by the voter.

## Phase 12 — Anchors only; the witness fallback is gone  (2026-09-04)

Whitepaper §9's degraded mode is removed rather than repaired. The reasoning
is in A16: a signature is not a clock, `W` of them are `W` keys rather than
`W` people once anyone can stand up an Issuer, and scoping them to the vote's
own electorate (Phase 11c) only narrowed the attack to the operators with the
most to gain. Anchoring needs none of that — it is permissionless, unpriced
through OpenTimestamps, covers everyone's items whoever made it, and is
checked against Bitcoin rather than believed.

- Item type `0x08` retired: `Witness`, `validate_witness`, `build_witness`,
  `Domain::Witness`, `WITNESS_THRESHOLD_W`, `LogView::witnesses_of` and
  `any_anchor_at_or_before` all deleted; decoding `0x08` is an error.
- The `Guarantee` enum and the wire `guarantee` field are gone with it: every
  counted ballot is anchored in Bitcoin at or before `close_block`, so there
  is nothing to qualify. `Outcome` is `Result { counts, counted }`,
  `BelowMinimum { counted }`, `NotClosed`, `Pending { missing_shares }`.
- `tally::timely_ballots` is now one filter: anchored at or before close.
- The node's witness role is gone, and **anchoring is on by default**
  (`--anchor on`, meaning OTS in a real deployment and the mock anchorer under
  `--dev`; `--anchor off` opts out). Several nodes anchoring the same items
  concurrently is harmless — the counting rule takes the earliest height — and
  a live five-node run shows exactly that, every node anchoring, three
  different anchors covering the three ballots.
- SPEC §1.6, §2 item table, §6.4, §6.7, §6.8 (retired in place, with why),
  §7.3, §12, §14, §15, §17.5 (vector removed, later ones renumbered);
  A16 rewritten, A49 marked superseded, A51 restated: **no node and no number
  of nodes has any say in a result**, so a network needs one honest reachable
  node, not a majority of them.
- Tests: `without_an_anchor_nothing_counts` (registered nodes present, no
  anchor, nothing counted; `0x08` no longer decodes; then one anchor from
  anyone and both ballots count), `unanchored_ballots_are_not_counted` in the
  verifier, and the hostile-cluster test now checks that the retired item type
  is refused.

Left alone deliberately: `whitepaper.md` still describes the fallback in its
item table (§6), §9 and the §14 constants table. That document is the source
of truth for the design and is the author's to change.
